# SOURCE — Technical Design Document (TDD)
## Master Architecture + AI Handoff Specification
**Version:** 1.0 — 2026-09-30

## 0. HANDOFF CONTRACT

This document is the working continuation specification for SOURCE / ATUNED. A receiving AI must read it before modifying the system, inspect the actual implementation and tests, preserve established terminology, and distinguish implemented, partial, designed, proposed, inferred, unverified, and blocked work.

Required loop:

```text
READ → AUDIT → MAP → IDENTIFY GAPS → PRIORITIZE → IMPLEMENT → TEST → RE-AUDIT → REPORT
```

Never invent missing Canon, never silently replace a source of truth, never convert a hypothesis into Canon without promotion evidence, and never claim completion without tests.

# 3. DATA ARCHITECTURE

Three primary layers:

| Layer | Purpose |
|---|---|
| Canon | Static shared reference content |
| User Record | Everything owned by one person |
| Server | Accounts, sync, entitlements, consent, operational storage |

Canon is read-only reference data. User records may reference Canon by key but do not contain Canon content.

The current user record contains personal onboarding, stories, release history, readings, longitudinal state, protocols, journal/progress state, consent, and the user lexicon.

The server is the trust boundary for account identity, entitlement, consent, and synchronization.

# 22. EMERGENT PATTERN ENGINE

## Purpose

The Emergent Pattern Engine is a distinct discovery and validation layer.

It asks:

> What repeatable structures exist in the observed data that SOURCE does not yet have names for?

It is not another level after hyper-complex.

It operates across the hierarchy:

```text
RAW FIELD
↓
KNOWN PATTERN ENGINE
+
UNRESOLVED FIELD
↓
EMERGENT PATTERN DISCOVERY
↓
CANDIDATE
↓
VALIDATION
↓
PROMOTION OR REJECTION
```

## Why it exists

The existing engine recognizes known architecture.

The discovery engine searches for:

- unnamed address combinations;
- cross-chakra combinations;
- cross-band combinations;
- recurring behavioral combinations;
- recurring somatic signatures;
- new saboteur-like structures;
- new complexes;
- new hyper-complexes;
- new relationships among existing structures.

# 34. POPULATION + LONGITUDINAL VALIDATION

When consented, privacy-preserving population data becomes useful for candidate validation.

Questions:

- Does it recur?
- How often?
- In what contexts?
- Is the behavior signature stable?
- Does it appear across people?
- Does it exceed the null model?
- Is it distinct from existing Canon?
- Does it persist longitudinally?
- Does it show consistent somatic registration?

Longitudinal example:

```text
DAY 1   candidate appears
DAY 7   repeats
DAY 21  repeats under another trigger
DAY 40  intervention
DAY 45  absent
DAY 90  returns
```

This supports a trajectory such as:

```text
DORMANT → TRIGGERED → ACTIVE → RELEASED → INTEGRATED → RECURRENT
```
